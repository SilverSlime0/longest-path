How it works

The goal. The score is the length of the shortest route from entry to exit, so a maze only counts if every way through it is long. A wall helps only if it forces the shortest route to detour.

Distance field (BFS). Starting from the exit, a breadth-first search labels every tile with its step count to the exit; the entry's label is the score. The heatmap shows these labels, each arrow points to the neighbor one step closer, and following the arrows from the entry traces the shortest path.

Blocking check. When you place a wall, the search runs again. If the entry gets no label, the exit has been sealed off and the wall is rejected.

Optimizer: simulated annealing. It repeatedly moves one wall, usually onto or next to the current shortest path (the only places a wall can lengthen it). A move that lengthens the path is always kept. A move that shortens it is sometimes kept, with a chance that shrinks as the "temperature" cools, so early on it explores and later it refines. Then a polish step tries every useful spot for each wall, and a prune step removes walls that do nothing.

Tie-break scoring. Among layouts with the same path length, the optimizer prefers ones with fewer shortest routes, so a half-built barrier counts as progress before it actually lengthens the path.

Small boards: annealing restarts. Short, independent annealing runs from random layouts; the best one wins. With only 6 walls, many fresh starts beat one long search that can get stuck. The number of restarts grows with the evaluation budget: one per 14 × walls² evaluations, which is 10 at the Optimize button's 5,000.

Medium and large boards: parallel tempering. Six annealers run at fixed temperatures, from hot (exploring) to cold (refining), and swap layouts now and then, so a good layout found while exploring gets refined. Moves sometimes shift 2–3 walls or slide a whole barrier, and the whole thing restarts from scratch so one unlucky start can't trap the whole run: one restart per 300 × walls² evaluations, which is 2 at the Optimize button's budget on both sizes. The lab shows how these compare with other methods.

Solve exactly (small boards). A layout can only beat the current one if it blocks a tile on the current shortest path, because otherwise that path still exists. So the search starts with no walls and, for every tile on the shortest path, tries adding a wall there, repeating until the wall budget is used. Wall sets it has already checked are skipped. Because every route to a better layout gets explored, the best one found is proven optimal. The catch is that the work grows exponentially with the number of walls, which is why this only runs on the small boards. The medium boards were proven offline by a faster version that also skips any branch where more separate short routes remain than walls are left; the large boards are beyond it.
